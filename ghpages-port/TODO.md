- [x] 3.1b Decision: the 10 MB upload cap stays. Photos fit comfortably; video and large downloads belong in a release asset or object storage and a link. Change `MAX_UPLOAD` in `browser-api/router.ts` if a site needs more, but note GitHub blocks files over 100 MB.
- [x] 3.1 Media upload: files go to an in-memory pending map, show in the tray as `Media` changes, persist in IndexedDB, and commit as blobs under `media/<key>`. - [x] 3.2 Media library: the `media` table (`content/media.json`) is the index, so no separate `_index.json`. Deleting a committed item shows in the tray as a deleted file and is committed as a removal.
- [x] 3.3 Pagefind index in the build (`pagefind --site dist/client` after the URL rebase), search UI in `src/pages/search.astro`. Only pages marked `data-pagefind-body` (posts and pages) are indexed.
- [x] 3.4 Scheduled publishing: the studio schedules through EmDash's own handler (fixed a facade bug where the options object was passed as the clock). At build, `ghdash-pages publish-due` runs the core sweep (`publishDue` from the browser API bundle) on `data.db`, then writes `content/` back; `pages.yml` runs hourly (cron `17 * * * *`), skips the build unless `ghdash-pages due` says something is due, and commits the published state to `main`. Published time is the scheduled time. Tested with a real database (`test/publish-due.test.mjs`) and the studio (e2e). Released in `pages-v0.6.0`. **Not covered:** picking the date in the admin's schedule dialog is not automated, only the API call.

## Phase 5: Plugins · est. 2–4 weeks
- [x] 5.1 Plugin UI in the studio for the bundled UI plugins `color`, `field-kit` and `embeds`. `createBrowserApi({ plugins })` reports plugins in the manifest and the studio passes `pluginAdmins` to the admin (adapter 0.6.0, `pages-v0.11.0`). `embeds` also renders at build time (`embedsPlugin()` in `astro.config.mjs`; a YouTube block became a `lite-youtube` element in a local build) and its blocks appear in the editor menu. Known limits: the manifest entry is copied by hand per plugin, and CI does not build a post that contains an embed.
- [x] 5.2 Browser before-save hooks (adapter 0.10.0, browser API from `pages-v0.15.0`): a plugin entry in `__STUDIO_PLUGINS__.plugins` can carry a plain `beforeSave({ data, collection, isNew, id })` function. It runs before every create and update in the studio and can rewrite the data or refuse the save with a message. Tested in the browser API suite (`browser-api/test.mjs`: rewrite, refuse a create, refuse an update, nothing saved after a refusal). It is site-written browser code, not the plugin's server hook; `content:beforePublish` and media hooks are not covered. `test.mjs` has one failing check, `users`, because the exported `content/` has no `users` table; that check predates this change.
- [x] 6.3a The round-trip CI test (`test/roundtrip.test.mjs` in the demo) found that a plugin's `_plugin_state` table, created in CI by the build, was exported to `content/`. Both the export and the studio tray now skip it (adapter 0.7.1). The demo's `data.db` is not otherwise part of the test.
- [x] 5.3 After-hooks in the Action: `ghdash-pages run-hooks` (adapter 0.7.0, release `pages-v0.12.0`) works out the changed content files between two commits, runs `content:afterSave` / `content:afterDelete` of the plugins in `hooks.config.json` with a minimal in-memory context, and `pages.yml` has a `hooks` job after the deploy that passes Actions secrets and remembers the last processed commit in the `hooks-last` tag. Tested with the real `webhook-notifier` and a fake `fetch`, and through the CLI in a temp git repo. The first real run on `main` passed (build, deploy, hooks) and created `hooks-last`; that push changed no content, so no webhook was sent. **Not covered:** a live webhook call (needs the `WEBHOOK_URL` secret), media hooks, plugins whose hooks need content or media access.
- [x] 5.4 Plugin cron (adapter 0.10.0): `ghdash-pages run-cron` runs the `cron` hook of plugins whose `hooks.config.json` entry lists `cron` jobs (`name`, `schedule` as a 5-field UTC cron expression or `@hourly`/`@daily`/`@weekly`, optional `data`) that fell due since the last run, and the demo's `pages.yml` has a `cron` job on the hourly schedule that remembers the last successful run in the `cron-last` tag. Unit tests cover the schedule maths and dispatch to the right plugin. **Not covered:** a real plugin cron job (none that can run in the Action exists in the repo); the `forms` and `ai-search` plugins still can't run there. Earlier note:  the plugins in the repo that use cron are `forms`, `ai-search` and `marketplace-test`. `forms` needs public routes and plugin storage, and `ai-search` needs content and AI access, which the Action's hook context doesn't have, so none of them could run there today. Build this when a plugin that can run in the Action needs a schedule; the hourly Action already exists to hang it on.
- [x] 5.5 Secret plugin settings stay out of the repo (adapter 0.7.2). EmDash stores a field declared `secret` as an encrypted envelope under `plugin:<id>:settings:<key>` and needs `EMDASH_ENCRYPTION_KEY`, which the browser does not have, so saving a secret in the studio fails instead of writing plaintext. As a second guard, the export and the studio tray both drop any such envelope row, with a unit test that fails without it. Secrets for Action-side hooks come from Actions secrets (`hooks.config.json`, 5.3). **Not checked:** how the studio words the failure when someone saves a secret field. A plugin that keeps a token in a field not declared `secret` is still published, which is the plugin's choice.
- [x] 5.6 The adapter README has a table of what works for each plugin (`color`, `field-kit`, `embeds`, `webhook-notifier`): in the studio, on the published site, and what doesn't work. It also states the two limits that hit every plugin: no public plugin routes, and no secret settings in the studio.
- [-] 5.7 Not building yet (decision 2026-11-14): no plugin in the repo needs it. Everything that can run without a server already runs in the browser (admin UI, `beforeSave`) or the Action (after-hooks, cron). Revisit when a plugin needs content or media access in the Action, or when someone wants marketplace plugins. Original idea: (Later) Sandboxed plugin runner (Web Worker or Node), and installing marketplace plugins by committing their code.
